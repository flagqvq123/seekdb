# 08 人机协作：规模、方式与 conversation.json

> 这一项直接对应 40 分（Agent Prompt 评价）。评的不是"Agent 多能干"，而是
> **你能不能证明自己理解了、验证了、修正了**。所以协作方式要从"能留下证据"倒推。

## 1. 协作规模建议（先定这个，再谈材料和分工）

| 角色 | 人数 | 每天有效投入 | 职责 |
|---|---|---|---|
| 你（决策/验证/复盘） | 1 | 1~2 小时 | 定优先级、验收结果、质疑方案、写自己的理解与复盘 |
| Lead（我） | 1 | 全程 | 架构与集成、写核心代码、统一提交、调度子智能体 |
| 子智能体 | 2~4 并行 | 1~3 小时/轮 | 文件边界清晰的独立模块（存储、性能、验证、文档） |

**规模原则**
1. 每个子智能体只写自己负责的文件（不重叠），接口由我定义 → 避免互相踩。
2. 每个任务必须有"可验收标准"（cargo test 全绿 / 某组用例 PASS / 有实测数字）。
3. 主线优先级：**功能准入 > 性能 > 材料**。功能准入不过，全部为 0。
4. 你不需要看懂所有代码，但必须能对每一块说出"它保证什么、怎么验证、坏了会怎样"。

## 2. 每轮怎么协作（20~40 分钟一个可验收小目标）
~~~text
1. 我：给下一个小目标 + 验收命令（例如"存储落地后 20/20 公开用例转绿"）
2. 子智能体：实现 + 自测 + 报告
3. 你：亲自跑验收命令（不要只看我的转述），把输出/截图留档
4. 你：问三个问题中的一个：
   - 这个改动影响哪条赛题要求？（对应性）
   - 怎么证明它真的对，而不是碰巧过？（验证设计）
   - 如果它失败，最可能错在哪？（故障假设）
5. 我：回答 + 必要时补实验；你：写下 2~3 行结论（这是复盘证据）
~~~

**关机/离开前的固定动作**：让子智能体进入"收尾模式"（写完整当前文件、可编译、
不启动长任务）→ 我统一 commit + push → 记录下次恢复点。

## 3. 五类证据怎么产生（对应评分维度）
| 维度 | 什么算"有效证据" | 今天已有的素材 | 需要你补什么 |
|---|---|---|---|
| 问题理解与自主拆解 | 你解释约束、识别难点、拆任务 | 你要求"先建目录/确认 gh/读文档/改分支"，先处理分支问题 | 用你自己的话说明为什么先做分支、为什么优先级这样排 |
| 技术理解与迁移 | 你用自己的话解释机制、预测新场景行为 | 尚无 | 例如："我理解 WAL 是先写日志再改数据，所以崩了能重放"；"ann 能降级是因为召回只要求 0.95" |
| 独立验证与质疑 | 你设计验证、跑出结果、指出错误 | 我发现的协议疑点、你的"文档读不了先暂停"判断 | 你亲自跑一次公开用例/加固用例，贴结果；质疑我某个结论 |
| 实验与反馈迭代 | 假设→实验→解释→修正→复测闭环 | 13/20 → 定位 7 个失败 → 修语句回滚/VARCHAR → 再跑 | 你参与其中一轮：提出假设、看结果、决定下一步 |
| 取舍与反思 | 解释代价、失败原因、局限 | ANN 降级、性能 vs 正确性 | 你用自己的判断解释一次取舍（例如为什么不做 HNSW） |

**计分档位提醒**：只提想法=0.5；有真实验证结果=1；解释结果并修正+复测=1.5；
迁移到新场景并分析局限=2。**同一个问题/修正链只算一个实例，只取最高档。**

## 4. conversation.json 大纲（建议结构，最终以你确认为准）
硬约束：路径 `agent/conversation.json`；UTF-8；合法 JSON 顶层对象；**≤128 KiB**；
不含密钥/令牌；不得编造；合成材料必须标 `synthetic: true`；
引用要能定位（RFC6901 JSON Pointer + ≤240 字符原文）。

~~~json
{
  "meta": {
    "version": "v1",
    "title": "MiniVectorDB 开发与验证记录",
    "synthetic": false,
    "scope": "2026-11-11 起的真实协作记录（脱敏后）",
    "redactions": ["个人路径/账号已脱敏"]
  },
  "user_prompts": [
    {"id": "u1", "content": "先创建工作目录、确认 gh、读文档，再从分支更改开始……", "context": "项目启动"}
  ],
  "conversations": [
    {"id": "c1", "role": "student", "content": "……", "ref": "u1"},
    {"id": "c2", "role": "agent",  "content": "……", "ref": "u1"},
    {"id": "c3", "role": "tool",   "content": "protocol_check 输出：13/20 PASS……", "ref": "e1"}
  ],
  "experiments": [
    {
      "id": "e1",
      "hypothesis": "7 个失败用例都源于重启丢数据，而不是 SQL 语义错误",
      "command": "bash minivectordb/tools/wsl_check.sh",
      "output": "PASS 13 / 20；失败均为 storage_*/transaction_* 的 --restart 行",
      "student_interpretation": "（你写自己的解释）",
      "fix": "实现 WAL 持久化",
      "retest": "（复测结果）"
    }
  ],
  "retrospective": [
    {"id": "r1", "topic": "为什么 ann 索引可以降级", "takeaway": "（你写）", "evidence": ["e1"]}
  ],
  "limitations": ["未实现 JOIN/聚合/子查询，按赛题要求返回错误"]
}
~~~
评分时，每个"实例"要给出：`student_evidence`（你的原文位置+片段）和
`result_evidence`（实际结果位置+片段），两者不能是同一段文字。

## 5. 我需要你提供的（材料部分）
1. 本次及后续对话的**原始 prompt**（我可以从会话记录提取，你确认哪些可公开）。
2. 2~3 次**你亲自执行的验收**（命令 + 输出 + 你的判断）。
3. 2~3 段**你自己的解释/质疑**（可以口语、可以短，但要是你的话）。
4. 3~5 条**复盘**（这次为什么这样取舍、哪里踩坑、下次怎么改）。
5. 脱敏口径：哪些路径/账号/截图不能出现。

我会负责：结构、引用定位、去重、体积控制（≤128 KiB）、与源码同 commit 提交。
**注意：我不会替你编造"你理解了"的内容**——那既不真实，也会被评审识破。
