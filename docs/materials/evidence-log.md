### 实例 E1：持久化失败的定位（对应维度：独立验证与质疑 / 技术理解）
问题场景：13/20 公开用例通过，7 个失败全部发生在 `--restart` 之后的第一条 SELECT，
报错统一为 `table_not_found`；同进程内重启前的 SQL 全部正确。

学生回答（原文）：
> 第一个问题肯定是1，因为在未完成磁盘存储层的情况下所有的存储和查询均在进程的内存中进行。做实验也很简单，创建一个表并导入数据后看看真实磁盘中有没有真正占用空间的存储目录就行了。

- 学生判断：原因 1（写的时候没落盘）
- 学生设计的验证：建表+导入数据后，检查磁盘上是否有实际占用空间的存储目录
- 实际结果（工具，context）：当时的 DiskStorage 为内存占位实现，/data 下无数据文件；
  修复后（WAL 落地）同一批用例 20/20 通过。 → 学生的判断与验证方向与实际根因一致。

### 实例 E2：过滤后 TopK 的语义与"看不出错"的条件（对应维度：技术理解与迁移 / 取舍与反思）
问题场景：4 行数据，id=1,2 的 category=skip 且距离 0；id=3,8 的 category=keep 且距离 1；
查询 `WHERE category='keep' ORDER BY distance LIMIT 1`。
正确实现返回 id=3（距离并列按主键升序）；"先全表取 Top1 再过滤"返回空集。

学生回答（原文）：
> 第二个问题的核心在于topk的定义是过滤后的，从逻辑上来说应当先完成过滤，再在剩余的集合中取k。如果反过来先K再过滤，只要有任何一个没被过滤掉的行存在于topk中就会错误，反之正确。例如这里把id为1，2的category改成keep，筛选前后topk的候选名单没有变，则结果就看上去正确。

- 学生解释：TopK 的定义域是过滤后的集合，必须"先过滤再取 K"
- 学生给出的"看不出错"条件：过滤后的候选名单与全表 TopK 名单一致时（例：把所有行的 category 都改成 keep）
- 待补充的边界（Lead 提示后由学生确认，见下条）：
  * 当 LIMIT k >= 总行数时，先取 K 再过滤 == 先过滤再取 K（因为"Top-k"就是全表）
  * 当 top-k(全表) 中不含任何被过滤行时，两者结果一致
